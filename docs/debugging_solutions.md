# SyncForge debugging solutions

1. **Duplicate webhook:** `WebhookEvent.count` and `SyncJob.count` should each increase once. The fast Ruby lookup handles normal redelivery; the unique indexes on `external_event_id` and `webhook_event_id` close concurrency races. A duplicate response is `200` with `duplicate: true`.
2. **HTTP 429:** `Clients::ErpClient` raises `RateLimitError` with `Retry-After`. The processor records `RETRYING`; Sidekiq schedules the next attempt using that delay. Repeated immediate calls indicate lost header parsing or bypassed error classification.
3. **Stuck queued job:** `/health` distinguishes Redis and Sidekiq. If Redis is healthy but Sidekiq has zero processes, start/fix the worker. If processes exist, confirm the worker consumes `syncs`; this project starts Sidekiq with `-q syncs -q default`.
4. **Missing email:** The customer transformer raises `DataValidationError`. The job and webhook become failed, with a `failed` SyncEvent and `failure_message`. Correct the CRM record or event snapshot before replaying because this error is deterministic.
5. **Bad authentication:** HTTP 401 maps to `AuthenticationError`, a non-recoverable error. Automatic retries would repeat invalid credentials and add load. Rotate/fix credentials, then manually replay the failed job.
6. **Redis unavailable:** Health becomes degraded. Existing workers cannot consume queued work and Sidekiq enqueue may fail. If only the rate limiter loses Redis during execution, it logs and fails open, protecting continuity at the cost of potentially exceeding ERP limits.
7. **High p95 latency:** A high p95 with a modest average indicates tail latency. Compare `started_at`/`completed_at` and SyncEvents, then inspect Sidekiq queue latency and ERP response time. This v1 metric excludes pre-start queue time, which is a documented observability gap worth adding.
8. **Intermittent HTTP 500:** HTTP 500 maps to `TemporaryServiceUnavailable`. Each execution increments `attempt_count`, records `processing` then `retrying`, and uses exponential backoff. Restoring ERP lets a later attempt reach `SUCCEEDED`; exhausting five retries creates `retry_exhausted` and `FAILED`.
